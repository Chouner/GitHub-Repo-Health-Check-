# RepoScope 项目设计文档

> GitHub 仓库健康度体检仪表盘 — 从需求到实现的完整记录

---

## 一、项目定位

**RepoScope** 是一款开源项目健康度体检工具。用户输入任意公开 GitHub 仓库 URL，系统自动聚合分析该仓库的各项指标，并以可视化仪表盘形式呈现。支持规则引擎和 AI 大模型双重评分。

**核心价值**：帮助开发者在选用开源依赖前快速评估项目质量，降低"踩坑"风险。

---

## 二、需求分析

### 2.1 核心功能

| 模块 | 内容 |
|---|---|
| 基础信息 | 名称、描述、作者、创建时间、更新时间、仓库大小、默认分支 |
| 热度指标 | Stars、Forks、Watchers、Open Issues |
| 活跃度指标 | 最后推送时间、最新 Release、Contributors 数量 |
| 代码结构 | 语言分布百分比条 + 图例 |
| 社区健康度 | Issue 关闭率、PR 合并率、未关闭 Issue/PR 数量 |
| 文档质量 | README / LICENSE / CONTRIBUTING / CHANGELOG 是否存在 |
| 类别识别 | 23 种类别标签自动判定（Web 框架、AI/大模型、DevOps 等） |
| 双评系统 | 规则引擎评分 + AI 模型评分，统一 100 分加权平均 |
| 历史记录 | localStorage 持久化，最多 20 条，支持一键回看 |

### 2.2 非功能需求

- **配置持久化**：GitHub Token 和 AI API Key 均在前端配置，存入 `localStorage`，刷新不丢失
- **离线可用**：即使不配置 AI，规则评分引擎始终可用
- **速率保护**：无 Token 时请求节流（每批 3 个，间隔 2s），避免触发 GitHub 二级速率限制
- **错误引导**：速率限制、Token 失效等错误均提供一键打开设置页面的引导链接

## 三、技术方案

### 3.1 架构

```
浏览器 (SPA)                Express Server                外部 API
┌──────────┐   /api/analyze  ┌──────────────┐   12+ 端点   ┌──────────┐
│ 输入 URL ├────────────────→│ URL 解析      ├────────────→│ GitHub   │
│ Dashboard│←────────────────│ 数据聚合      │←────────────│ REST API │
│ 双评对比  │                │ 规则评分      │             └──────────┘
│ 历史记录  │   /api/ai-score │              │             ┌──────────┐
│ AI 配置  ├────────────────→│ AI 路由分发   ├────────────→│ OpenAI   │
└──────────┘                │ 结果解析      │             │ DeepSeek │
                            └──────────────┘             │ Kimi     │
                                                         │ ...      │
                                                         └──────────┘
```

### 3.2 技术选型

| 层级 | 技术 | 选型理由 |
|---|---|---|
| 前端 | HTML + Vanilla JS + Tailwind CSS CDN | 零构建步骤，无框架依赖，直接部署 |
| 图表 | Chart.js CDN | 轻量、无需构建 |
| 后端 | Node.js + Express | 与前端同语言，GitHub API 代理 + AI 路由 |
| HTTP 客户端 | node-fetch | 轻量，兼容 fetch API |
| AI 对接 | OpenAI 兼容接口 + Anthropic 原生接口 | 覆盖 6 家厂商 |

### 3.3 数据流

```
1. 用户输入 URL → 前端 POST /api/analyze { url, githubToken? }
2. 后端解析 owner/repo → 分批节流拉取 7 个 GitHub API 端点
3. 聚合数据 + 规则评分 + 类别判定 → 返回结构化 JSON
4. 前端渲染仪表盘（双评行 + 维度卡 + 关键指标 + 语言分布 + 社区健康）
5. 用户点击 "AI 评分" → POST /api/ai-score { repoData, provider, apiKey }
6. 后端路由到对应厂商 → 注入提示词 → 解析返回 → 更新评分行
```

## 五、评分算法

### 5.1 设计原则

两套评分共用**相同的维度和权重**，总分 = 各维度 × 权重的加权平均，统一 100 分制，确保可对比。

### 5.2 维度与权重

| 维度 | 权重 | 规则引擎评估方式 | AI 评估方式 |
|---|---|---|---|
| 社区热度 | 25% | Stars 对数映射 (log₁₀×25)，10k 星满分 | 综合 Star/Fork/Watch/Topic |
| 维护活跃度 | 25% | 最后推送天数线性衰减 (100-days×100/365) | 更新时间、提交频率、Release 频率 |
| 文档完整度 | 20% | README(40)+LICENSE(25)+CONTRIBUTING(20)+CHANGELOG(15) | 文档存在性及质量 |
| 工程规范 | 15% | 依赖文件(40)+测试目录(30)+CI 配置(30) | 目录结构、CI、测试、依赖管理 |
| 可持续性 | 15% | Releases(40%)+Contributors(35%)+Topics(25%) | 贡献者、Issue 处理、PR 活跃度 |

**等级阈值**：≥85 优秀 / ≥70 良好 / ≥50 一般 / <50 风险较高

### 5.3 规则评分演进

| 版本 | 算法 | 问题 |
|---|---|---|
| v1 | 绝对阈值叠加（Stars>10k=25, Stars>1k=20...） | 各维度子分数范围不统一（有的 25 分满分，有的 15 分满分），无法与 AI 评分对比 |
| v2（当前） | 每维度 0-100 分，加权平均 | 与 AI 评分尺度一致，可直接对比维度差异 |

### 5.4 评分明细（Breakdown）

每个维度均可点击展开评分明细，包含：
- **规则评分**：详细计算公式 + 数据依据 + 缺失项标注（✅/❌/⚠️/🔴）
- **AI 评分**：AI 返回的结构化说明（如缺失则从 strengths/risks/suggestions 自动构造）

## 六、AI 提示词设计

### 6.1 项目综合评分 Prompt（最终版本）

```
你是一个资深开源项目评估专家。请根据下面的 GitHub 仓库数据，对该项目进行健康度评估。

请从以下维度评分（每个维度 0-100 分），总分按加权平均计算：
1. 社区热度（权重 25%）：Star、Fork、Watch、Topic 数量
2. 维护活跃度（权重 25%）：最近更新时间、提交频率、Release 频率
3. 文档完整度（权重 20%）：README、LICENSE、CONTRIBUTING、CHANGELOG 是否存在及质量
4. 工程规范（权重 15%）：目录结构规范性、CI 配置、测试覆盖、依赖管理
5. 可持续性（权重 15%）：贡献者数量、Issue 处理情况、PR 活跃度、生态成熟度

总分 = popularity×0.25 + activity×0.25 + documentation×0.20 + engineering×0.15 + sustainability×0.15

请输出纯 JSON（不要包含 markdown 代码块标记），格式如下：
{
  "totalScore": 0,
  "level": "优秀 / 良好 / 一般 / 风险较高",
  "scores": { "popularity": 0, "activity": 0, "documentation": 0, "engineering": 0, "sustainability": 0 },
  "summary": "一句话总结项目健康状态",
  "strengths": ["优势1", "优势2", "优势3"],
  "risks": ["风险1", "风险2"],
  "suggestions": ["建议1", "建议2", "建议3"],
  "breakdown": {
    "popularity": ["数据依据：Stars N，Forks N", "评分理由：...", "结论：✅/📌/⚠️/🔴 ..."],
    "activity": ["数据依据：最后推送 N 天前", "评分理由：...", "结论：✅/📌/⚠️/🔴 ..."],
    "documentation": ["数据依据：README=是/否，LICENSE=是/否", "评分理由：...", "结论：..."],
    "engineering": ["数据依据：package=是/否，tests=是/否，CI=是/否", "评分理由：...", "结论：..."],
    "sustainability": ["数据依据：Releases N，Contributors N，Topics N", "评分理由：...", "结论：..."]
  }
}

注意：breakdown 中每个维度的数组最多 5 行，每条以 ✅(优势) / ❌(缺陷) / 📌(中性) / ⚠️(风险) / 🔴(严重风险) 开头。

仓库数据如下：
{{repoData}}
```

### 6.2 Prompt 设计要点

| 要素 | 说明 |
|---|---|
| 角色设定 | "资深开源项目评估专家" - 设定专业领域 |
| 明确权重 | 在 Prompt 中显式给出公式，确保 AI 总分计算与规则引擎一致 |
| 结构化输出 | 要求纯 JSON（无 markdown 包裹），减少解析出错 |
| 枚举约束 | level 限定为 4 个等级、breakdown 限定每维度 ≤5 行 |
| 图标标记 | ✅/❌/📌/⚠️/🔴 作为每条明细的前缀，前端可直接按色渲染 |
| 数据注入 | `{{repoData}}` 为后端聚合后的完整 JSON，包含所有维度的客观数据 |

### 6.3 多厂商兼容

后端实现了统一的 `callAI()` 分发器，OpenAI / DeepSeek / Kimi / 豆包 / Qwen 使用 **OpenAI 兼容协议**（`/v1/chat/completions`），Claude 使用 **Anthropic 原生协议**（`/v1/messages`）。同一套 Prompt 可适配所有厂商。

## 七、类别识别

### 7.1 算法

基于 **关键词匹配 + 加权打分**，扫描仓库的 `topics` / `description` / `language` / `name` / 目录结构：

```
fullText = description + topics + language + name + dirNames
for each category:
    for each keyword:
        exact match (+5) + partial match (+1)
return top-scoring category
```

### 7.2 类别列表（23 类）

AI/大模型、机器学习/深度学习、Web 框架、前端组件库、CLI 工具、数据库/存储、DevOps/CI-CD、API/后端服务、移动开发、桌面应用、编程语言/编译器、测试框架、文档/静态站点、数据科学/分析、安全工具、游戏引擎/开发、构建工具/打包器、编辑器/IDE、网络/协议、消息队列/事件、监控/可观测性、工具库/SDK、操作系统/底层

## 八、实现过程中的问题与解决

| # | 问题 | 解决方案 |
|---|---|---|
| 1 | GitHub API 无 Token 仅 60次/小时，13 并行请求瞬间耗尽 | 减少到 7 次（合并 state=all、复用目录列表检测文档）+ 分批节流（每批 3 个，间隔 2s） |
| 2 | `github_pat_` 前缀的 fine-grained token 认证格式差异 | 统一使用 `Authorization: token xxx` 格式（GitHub REST API 兼容） |
| 3 | 前端刷新后配置丢失 | GitHub Token + AI 配置存入 `localStorage`，启动时自动恢复 |
| 4 | 规则评分和 AI 评分数值不可对比 | 统一为 0-100 分加权平均，每维度独立打分，总分为维度分×权重 |
| 5 | 低分维度用户不理解原因 | 添加 breakdown 字段，每维度可点击展开详细计算过程 |
| 6 | AI 返回 JSON 可能包裹在 markdown 代码块中 | `parseAIResponse()` 正则提取 ` ```json ... ``` ` 块再解析 |
| 7 | 速率限制错误缺少操作引导 | 错误消息带 `github_rate_limit||` 前缀，前端识别后渲染带链接的引导文案 |

## 九、后续可优化方向

### 9.1 功能增强

- [ ] **Commit 活跃趋势图**：拉取近 12 个月提交统计，绘制柱状图
- [ ] **Issue / PR 趋势**：Issue 响应时间、PR 合并时间趋势分析
- [ ] **README 内容分析**：调用 AI 对 README 内容质量做深度分析（已有 Prompt 模板）
- [ ] **贡献者排行**：展示 Top 贡献者及其贡献量
- [ ] **依赖分析**：解析 package.json / go.mod 等，展示依赖树与版本信息
- [ ] **分享报告**：生成可分享的 Markdown / 图片报告
- [ ] **批量对比**：同时分析多个仓库并横向对比
- [ ] **组织分析**：输入 GitHub 组织名，批量分析下所有仓库
- [ ] **暗色模式**：支持 light/dark 主题切换
- [ ] **多语言支持**：中英文界面切换

### 9.2 性能优化

- [ ] **服务端缓存**：相同仓库 N 分钟内复用缓存结果，减少 API 调用
- [ ] **浏览器端 IndexedDB**：完整分析结果持久化，离线可查看历史报告
- [ ] **增量更新**：分析过仓库后，仅拉取增量数据（用 ETag / If-Modified-Since）
- [ ] **Web Worker**：将规则评分和类别识别移到前端 Worker 线程

### 9.3 评分优化

- [ ] **规则评分引入 Fork 和 Watch 数据**：当前仅用 Stars 代表社区热度
- [ ] **OpenRank 指数集成**：引用开源项目的标准化影响力指标
- [ ] **安全评分维度**：检测依赖漏洞、不安全配置等
- [ ] **许可证合规评分**：检测许可证兼容性
- [ ] **多 AI 评分取平均**：同时调用多个模型，展示评分分布

### 9.4 工程化

- [ ] **打包工具**：引入 Vite 构建，优化 Tailwind 按需编译
- [ ] **前端框架迁移**：考虑 React/Vue 重写以支持更好的组件复用
- [ ] **API 限流**：后端添加请求频率限制中间件
- [ ] **单元测试**：规则评分引擎和类别识别函数的测试覆盖
- [ ] **TypeScript 迁移**：前后端类型安全
- [ ] **GitHub OAuth 登录**：用户登录后直接使用 GitHub Token，无需手动配置

## 十、前端原型设计参考

早期使用设计工具生成了 HTML 原型（`RepoPulse AI`），包含 SVG 环形仪表盘、Tailwind CSS 主题色彩系统、Material Symbols 图标等设计语言。最终实现保留了原型的视觉基调（蓝绿配色、JetBrains Mono 等宽字体、圆角卡片），但将静态原型改造为动态 SPA。
